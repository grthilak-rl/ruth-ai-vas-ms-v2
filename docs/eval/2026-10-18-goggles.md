# `goggles` store-model evaluation — HPCL camera 75096, 2026-10-18

Handover for the AI engineer. Companion to `../2026-10-17/`, which
covered `gloves`, `hard_hat` and `safety_vest`.

**`goggles` does not transfer to HPCL imagery.** On 32 recent frames from
camera 75096 it emitted 17 boxes, all of the *compliant* class, peaking at
**0.276** — below the manifest's `min_confidence` of 0.5. It produced
**zero `no-goggles` boxes at any confidence down to 0.01.** As configured
it cannot fire.

**It has nevertheless been installed and enabled for a live test**, at the
operator's decision and over this recommendation. The reasoning is sound
and is recorded under "Why it was installed anyway" below: this sample is
small, single-camera and biased by construction. Live streaming frames are
a different and larger sample.

**The headline for training purposes: this model's validation metrics did
not predict its field behaviour.** It scores mAP50 0.898 — second only to
`safety_vest` — and still produces nothing usable here. See "The metric
trap".

Everything here is read-only evidence. The only change made to the
deployment was installing the model afterwards.

## Results on these 32 frames

Baseline: 44 person boxes across 29 of 32 frames, median head height
**76 px**.

| | uploaded `bestgoggles.pt` | built-in control |
|---|---:|---:|
| total boxes | 17 | 41 |
| `goggles` — n / max / median | 17 / **0.276** / 0.068 | 30 / **0.641** / 0.049 |
| `no-goggles` — n / max | **0 / —** | 11 / 0.366 |
| frames with any box ≥ 0.25 | 2 / 32 | 4 / 32 |
| frames with any box ≥ 0.5 | **0 / 32** | 3 / 32 |

The control is the built-in PPE detector's own goggles head
(`ai/models/ppe_detection/1.0.0/weights/both_classes/goggles.pt`), run on
the identical frames. It is **not** a good model either — but it reaches
0.641 and does emit the violation class, which establishes that these
frames are hard rather than impossible. The uploaded weights are
specifically weaker on this imagery than the ones they were meant to
replace.

## What was ruled out

**This is not the `hard_hat` situation.** The `hard_hat` evaluation was
declared inconclusive because nearly everyone in the sample wore a hard
hat, so zero fires was also what a correct model would do. That defence
does not apply here. Look at `goggles-75096.jpg`: many workers wear
clearly visible dark eye protection, and others plainly wear none. **Both
classes are present**, and the model detects neither with confidence.

Decisively, the class it *does* emit is the compliant one — the class that
is abundantly present — and it still cannot exceed 0.276 on it. A
class-balance artefact cannot explain that.

**Class-order mapping.** Read from the weights, not assumed:

| | weights `model.names` | manifest `classes` | match |
|---|---|---|---|
| `goggles` | `{0:'goggles', 1:'no-goggles'}` | identical | ✅ |

Same polarity as `gloves` and `hard_hat` (compliant class at index 0). It
is `safety_vest` that is inverted. The trap that bit us before is not
present here.

**Resolution.** Not the cause. Same frames, whole scene preserved, at
three input sizes:

| | imgsz 1280 | 1920 | 2560 |
|---|---:|---:|---:|
| uploaded, best `goggles` | 0.276 | 0.000 | 0.342 |
| built-in, best `goggles` | 0.641 | 0.555 | 0.308 |

Flat and erratic for the uploaded model; actively *worse* for the control.
Both are best at their trained imgsz. More pixels will not rescue this.

**Head-crop tiling.** Would make it worse, not better. Magnifying the head
region 4× and 8× collapses **both** models:

| | ×1 | ×4 | ×8 |
|---|---:|---:|---:|
| uploaded, best any class | 0.034 | 0.040 | 0.044 |
| built-in, best any class | 0.136 | 0.150 | 0.151 |

The control falls from 0.641 on the full frame to 0.151 on a crop of the
same head. Both models depend on whole-scene context, so a crop-and-zoom
pre-pass is not an available workaround. (This test was originally
intended as the scale test; it confounds scale with context removal, which
is why the imgsz sweep above was run instead. It is kept because the
negative result is itself useful.)

**imgsz mismatch.** None. Trained at 1280, inferred at 1280.

## The metric trap

These checkpoints carry `train_metrics` and `train_results`, which the
2026-10-17 evaluation did not know to look for. Reading all four:

| model | mAP50 | mAP50-95 | precision | recall | val cls_loss | train cls_loss | base | field result |
|---|---:|---:|---:|---:|---:|---:|---|---|
| `safety_vest` | 0.942 | 0.812 | 0.909 | 0.886 | 0.54 | 0.19 | yolov8m | works |
| **`goggles`** | **0.898** | **0.627** | **0.766** | **0.899** | **1.20** | **0.25** | yolov8m | **inert** |
| `hard_hat` | 0.888 | 0.732 | 0.775 | 0.844 | 0.74 | 0.68 | yolov8n | inconclusive |
| `gloves` | 0.533 | 0.253 | 0.568 | 0.559 | 2.09 | 0.20 | yolov8m | inert |

Two things follow.

**The metrics would have caught `gloves` before it ever reached the
plant.** mAP50 0.533 with a 10× val/train `cls_loss` gap is a textbook
overfit, and it was readable from the file on day one. This answers
suggestion 3 of the previous handover: the validation scores *are* being
recorded, under `train_metrics`, just not `best_fitness`.

**The metrics do not catch `goggles`.** It passes every screen — second-best
mAP50, the best recall of all four — and is useless in the field. Its only
warning sign is a val/train `cls_loss` ratio of 4.8×, higher than
`safety_vest`'s 2.8× but far below `gloves`' 10×.

So validation metrics are a useful *filter* and not a *gate*. The gap is a
domain gap: a model can fit its own validation split well and still fail on
refinery imagery that looks nothing like it.

## Why it was installed anyway

Recorded so the next reader does not mistake this for an oversight.

This sample has three real limitations, and the operator weighed them:

1. **32 frames from one camera.** Small.
2. **Snapshot frames exist *because* a vest or hardhat violation fired.**
   They are biased toward people being present, which suits this question,
   but they are not a random sample of what the model sees live and must
   not be used to estimate precision or recall.
3. **One site, one time of day.** Sunday morning, overhead sun, heavy
   shadow under hard-hat brims in most frames.

A live test on streaming frames samples far more broadly. The cost is
bounded: one extra consumer on one camera, about 2.7% of per-consumer
throughput, and no alert risk worth speaking of given the violation class
never fired at all here.

**One caveat the live test must account for.** In
`ai/store_plugin/inference.py` the rule's `min_confidence` is used as the
`model.predict(conf=...)` floor, not only as the alert threshold:

```python
floor = min((r["min_confidence"] for r in rules), default=0.25)
results = model.predict(frame, imgsz=manifest["imgsz"], conf=floor, ...)
```

At `min_confidence: 0.5`, boxes below 0.5 are never generated. Since the
observed maximum here is 0.276, **a live test at 0.5 will return exactly
zero and cannot distinguish "the model is blind" from "nobody was on
site".** To get a signal, lower the rule to 0.25 for the test window and
restart the store runtime. That is a diagnostic setting, not an alerting
one.

The dataset-naming pattern from the previous handover holds. The two
models that work on site came from *combined* datasets
(`combined vest.v2i`, `combined hardhat.v1i`). The two that do not —
`gloves` and now `goggles` — came from single un-combined exports with no
version suffix (`glovesmodel.yolov8`, `googlesmodel.yolov8`). Three of
three. Worth treating as a signal about dataset breadth.

## Suggested next steps

The engineer's call, not prescriptive:

1. **`goggles` needs retraining on refinery imagery, not retuning.** No
   threshold rescues a model whose best detection of the *compliant* class
   is 0.276. Lowering the rule to 0.25 would fire on noise.
2. **Train for the actual operating condition.** These cameras give
   **~76 px head height at oblique angles, under hard-hat brims, in hard
   overhead sun**. Goggles at that scale are roughly 40 × 15 px. If the
   training set is frontal close-ups, that is the gap. The frames in
   `frames/` are a free, if unlabelled, description of the target domain.
3. **Combine datasets**, per the three-of-three pattern above.
4. **Report `train_metrics` with every delivery**, and treat them as a
   filter rather than a gate — `goggles` passes them and fails the plant.
5. **Consider a single multi-class PPE model** rather than one model per
   item. Six separate models at 12 cameras is 72 consumers against a fixed
   `MAX_GPU/latency` fleet budget; one multi-class model with per-camera
   rule toggles is 12. This is already an open question on the roadmap and
   this evaluation does not settle it, but goggles makes the arithmetic
   concrete.

## Reproducing

```bash
docker run --rm --gpus all --user 1000:1000 \
  -e MPLCONFIGDIR=/tmp/mpl -e YOLO_CONFIG_DIR=/tmp -e HOME=/tmp \
  -v /mnt/storage/ruth-models/enabled/goggles/1.0.0/weights:/w:ro \
  -v /mnt/storage/ruth-models/eval/2026-10-18:/out \
  -v <this-dir>:/sp:ro \
  --entrypoint python ruth-ai-unified-runtime:2026.10-offload -I /sp/eval.py
```

`eval.py` reads `/snaps/75096` as written; point that mount at
`/mnt/storage/ruth-models/eval/2026-10-18/frames` to re-run against the
frozen copies rather than sampling new frames.
